# FitLife

Веб-приложение фитнес-клуба: клиент, тренер и администратор. Backend — Java 17+, Spring Boot, Spring Security, JPA, PostgreSQL и Flyway; frontend — HTML/CSS/JavaScript без внешних npm-зависимостей. Интерфейс обращается к REST API, данные сохраняются в БД. Старый деморежим с localStorage больше не используется.

## Запуск всего проекта

Нужен Docker Desktop с Linux-контейнерами и Docker Compose v2. Из корня проекта:

```powershell
Copy-Item .env.example .env
```

Открой `.env` в VS Code и замени примеры `DB_PASSWORD`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` своими значениями. Пароль администратора: не менее 8 символов, не более 72 байт UTF-8. Не коммить `.env`.

```powershell
docker compose up --build -d
docker compose ps
```

Сайт: http://localhost:3000. Проверка backend: http://localhost:8080/actuator/health. Первое скачивание образов и сборка требуют интернета. Контейнеры ждут готовности базы и backend.

Вход администратора — реквизиты `ADMIN_EMAIL` / `ADMIN_PASSWORD` из `.env`. Клиент регистрируется через сайт. В кабинете администратора открой «Тренеры → Добавить тренера», задай аккаунт и специализацию, затем создай занятия в расписании. Весь набор начинается с пустой БД и первого администратора; встроенных демопаролей и вымышленных клиентов нет.

Данные находятся в отдельном Docker-томе `fitlife_data`. Обычная остановка `docker compose down` их сохраняет. Параметр `down -v` удаляет том с БД — для обычной остановки его не используй. Старый том `pgdata` от прежней конфигурации не подключается и автоматически не удаляется.

Администратор создаётся только при отсутствии административных аккаунтов. Изменение `ADMIN_PASSWORD` в `.env` не сбрасывает пароль уже существующей записи. При перезапуске backend текущие веб-сессии завершаются; сами профили и записи остаются в PostgreSQL.

Логи и остановка:

```powershell
docker compose logs --tail=100 backend
docker compose logs --tail=100 db
docker compose logs --tail=100 backup
docker compose down
```

Порты опубликованы только на локальном компьютере. Для размещения в интернете нужны HTTPS reverse proxy и `COOKIE_SECURE=true`; текущая инструкция рассчитана на локальную учебную работу.

## Запуск через VS Code без общего Docker-запуска

Нужны JDK 17 или 21, Node.js 20+ и PostgreSQL. Можно запустить только БД из Compose:

```powershell
docker compose up -d db
```

Либо создай в установленном PostgreSQL базу `fitlife` с пользователем `fitlife`, чей пароль совпадает с `DB_PASSWORD`. Для другого адреса или имени БД задай `DB_URL` и `DB_USER` в окружении backend.

Первый терминал, из корня проекта:

```powershell
$env:JAVA_HOME = 'путь к установленному JDK'
.\scripts\start-backend.ps1
```

`JAVA_HOME` указывает на каталог JDK, а не `bin`. Если Java уже найдена в PATH, явное указание не нужно. Скрипт загружает нужные значения из `.env` и запускает Maven Wrapper. Maven отдельно устанавливать не требуется; при первом запуске он загрузит зависимости.

Второй терминал:

```powershell
cd frontend
.\start.cmd
```

Открой http://localhost:3000. Локальный Node-сервер раздаёт `frontend/src` и проксирует `/api` на `http://127.0.0.1:8080`. Для другого backend задай `API_URL` перед запуском frontend. Для другого порта frontend задай `PORT`. Установка npm-пакетов не требуется. Не открывай HTML через `file://` или Live Server: нужен прокси `/api`.

## Функции

- Клиент: регистрация и вход, профиль и рост, запись/отмена занятия, вес и жим лёжа по датам, графики и ИМТ, регистрация/отмена участия в событиях, уведомления.
- Тренер: только собственное расписание и участники, создание/редактирование/отмена своих занятий, просмотр записанных клиентов, уведомления.
- Администратор: клиенты и их активность, абонементы и сроки, создание и редактирование тренеров, общее расписание, события и черновики, показатели клуба.
- Гость: лендинг, регистрация и вход.

Изменения отображаются после загрузки раздела/действия или кнопки «Обновить». Обзор автоматически обновляется раз в 30 секунд, если пользователь не заполняет форму. WebSocket и синхронизация в реальном времени без опроса не используются.

Абонемент учитывается в профиле и редактируется администратором. На текущем этапе срок/тип абонемента не блокирует запись автоматически: бизнес-правила доступа по тарифам не заданы. Оплата не реализована.

## Данные и правила

Таблицы: `users`, `client_profiles`, `trainer_profiles`, `memberships`, `training_sessions`, `bookings`, `progress_records`, `events`, `event_registrations`, `notifications`; служебная таблица `mutation_lock`. Flyway управляет схемой, Hibernate использует `ddl-auto=validate`.

Уникальны почта без учёта регистра, пара клиент–занятие, пара клиент–событие и запись дневника на дату. Внешние ключи обеспечивают целостность. Удаление занятия/события удаляет связанные регистрации и создаёт уведомления участникам.

Занятие: 15–180 минут, 1–50 мест, только будущее время и активный тренер. Сервер проверяет пересечения у тренера, занятого зала и клиента. При переносе проверяются все уже записанные участники. Событие: 1–200 мест. Дневник: корректная прошедшая или текущая календарная дата, вес 25–350 кг, жим 0–500 кг; рост 80–250 см. Эти диапазоны — рабочие правила текущего приложения.

Мутации выполняются в транзакции после блокировки единственной строки `mutation_lock` в PostgreSQL. Это намеренно простое решение для небольшого учебного клуба: защищает вместимость и пересечения даже при нескольких экземплярах backend, но последовательно обрабатывает записи. Для большой нагрузки следует перейти к блокировкам конкретных ресурсов и более узким SQL-запросам.

Авторизация использует серверную сессию с HttpOnly/SameSite cookie. CSRF включён для всех изменяющих запросов, включая вход и регистрацию. После входа меняется идентификатор сессии. Пароли хешируются BCrypt. Публичная регистрация не принимает роль. Доступ и активность пользователя проверяются сервером; при приостановке аккаунта его существующая сессия перестаёт давать доступ.

Проверки ролей не зависят от видимости кнопок. Клиент получает только свой дневник и собственные персональные данные; другие участники в списках мест обезличены. Тренер получает данные клиентов, записанных на его занятия. Администратор управляет данными клуба.

## API

Запросы и ответы используют JSON. Для изменения данных сначала выполни GET `/api/auth/csrf`, сохрани cookie сессии и отправляй токен в заголовке, имя которого вернул сервер. После входа/регистрации получи новый токен. Ошибка имеет поля `status` и `message`; пустой успешный ответ операций записи — HTTP 200, выход — 204.

| Метод и путь | Назначение |
| --- | --- |
| GET /api/auth/csrf | CSRF-токен и имя заголовка |
| POST /api/auth/register | `{name,email,password}`; создание клиента и вход |
| POST /api/auth/login | `{email,password}`; вход |
| POST /api/auth/logout | Завершение сессии |
| GET /api/auth/session | Текущий пользователь |
| GET /api/snapshot | Снимок разрешённых текущей роли данных для кабинета |
| GET, PATCH /api/me | Профиль; изменение `{name,phone,height}` |
| GET, POST /api/trainings | Расписание; создание занятия |
| PATCH, DELETE /api/trainings/{id} | Изменение/отмена занятия |
| POST /api/bookings | `{trainingId}`; новая запись |
| DELETE /api/bookings/{trainingId} | Отмена своей записи на указанное занятие |
| GET, PUT /api/progress | Дневник; `{date,weight,strength}` |
| GET /api/clients | Клиенты, доступные текущей роли |
| PATCH /api/clients/{id} | `{name,phone,active,plan,planUntil}`; атомарное изменение карточки и абонемента |
| GET, POST /api/trainers | Список; создание тренера |
| PATCH /api/trainers/{id} | Изменение тренера, необязательный новый пароль |
| GET /api/memberships | Профиль и абонемент текущего пользователя |
| PUT /api/memberships/{clientId} | `{plan,planUntil}`; изменение администратором |
| GET, POST /api/events | Доступные события; создание |
| PATCH, DELETE /api/events/{id} | Изменение/удаление события |
| POST, DELETE /api/events/{id}/registration | Участие/отмена |
| GET /api/notifications | Последние 100 собственных сообщений |
| PATCH /api/notifications/{id}/read | Отметка прочтения |
| GET /api/statistics | Сводные показатели для администратора |

Поля занятия: `title, coachId, date, time, duration, capacity, room`. Для тренера сервер назначает его самого независимо от переданного `coachId`. Поля события: `title, description, date, time, type, capacity, published`. Поля тренера: `name, email, password, phone, specialty, active`; при изменении `password` можно не передавать. Даты — `YYYY-MM-DD`, время — `HH:mm`. Неизвестные поля в DTO отклоняются.

## Резервные копии и восстановление

Сервис `backup` создаёт дамп сразу после старта, затем каждые 24 часа; при ошибке повторяет попытку через минуту. Завершённые дампы появляются в `backups` на ПК, имеют формат PostgreSQL custom и не коммитятся. Автоматического удаления старых копий нет: контролируй свободное место и переноси нужные копии на отдельный носитель.

Ручная копия, из корня проекта:

```powershell
.\scripts\backup.ps1
```

Восстановление **заменяет текущие данные** выбранной копией. Сначала сохрани свежий дамп, затем выполни:

```powershell
.\scripts\restore.ps1 -BackupFile '.\backups\имя-копии.dump'
```

Скрипт останавливает приложение и службу копирования, восстанавливает БД одной транзакцией, затем запускает сервисы. При ошибке восстановления приложение остаётся остановленным. Используй копию той же версии схемы приложения. После восстановления войди заново.

## Проверки

```powershell
cd backend
.\mvnw.cmd test
.\mvnw.cmd package
cd ..\frontend
node --test tests/api.test.mjs
node build.mjs
```

Backend-тесты запускают временный настоящий PostgreSQL через тестовую зависимость Embedded Postgres; Docker для этих тестов не нужен. Тестовая БД изолирована от пользовательской. Требуются доступ к Maven Central при первом запуске и разрешение запуска локальных PostgreSQL-процессов.

Проверены 9 серверных интеграционных тестов и 2 клиентских теста: авторизация, CSRF и ротация сессии, роли, некорректная дата, границы антропометрии, владение занятиями, пересечения и перенос участников, конкуренция за последнее место, абонементы, блокировка аккаунта, события, приватность уведомлений, сохранность данных после перезапуска приложения. Несколько сценариев проверяются внутри каждого теста.

В браузере проверены вход трёх ролей, создание тренера и занятия, регистрация клиента, запись, сохранение после обновления, дневник и прочтение уведомления. Тесты выполнялись на PostgreSQL 14.15; Compose настроен на PostgreSQL 17. Docker-сборка, контейнерный запуск и скрипты резервного копирования/восстановления в этой среде не запускались, поскольку Docker отсутствует.

Для разработчика есть необязательный `BrowserTestServer` в тестовых исходниках — временный стенд с отдельной PostgreSQL и портом 8081. Требует переменных `ADMIN_EMAIL` и `ADMIN_PASSWORD`; данные после завершения стенда не являются пользовательской БД.

## Границы текущего этапа

Реализованы веб-приложение и серверное хранение. Push на устройства, мобильное приложение, онлайн-оплата и автоматическое перемещение старых браузерных демоданных в PostgreSQL не входят в эту реализацию. Уведомления работают внутри открытого кабинета. Резервное копирование хранит копии локально; внешнее хранилище не подключено.
