# Frontend FitLife

Адаптивный frontend для существующего проекта `kpo_gym`. Реализован на HTML, CSS и JavaScript с ES-модулями, без внешних зависимостей. Интерфейс работает отдельно от Spring Boot. Никакие внешние изображения, шрифты, CDN или сервисы не требуются.

## Быстрый запуск

Открой `web/start.cmd` двойным щелчком. Оставь окно сервера открытым и перейди на [http://localhost:3000](http://localhost:3000).

Или в терминале из папки проекта, при установленном Node.js 20+:

```powershell
cd web
node server.mjs
```

Установка npm-пакетов не нужна. Если порт занят, останови предыдущий сервер либо задай другой порт:

```powershell
$env:PORT = '3001'
node server.mjs
```

Отдельный запуск frontend в Docker из корня проекта:

```powershell
docker compose -f docker-compose.frontend.yml up --build
```

Основной `docker-compose.yml` не изменён. В нём пока есть отдельные проблемы backend: различаются параметры базы и пользователя PostgreSQL, а зависимость `service_healthy` не сопровождается healthcheck. Сам backend ещё не содержит API и конфигурации подключения к БД. Поэтому для просмотра frontend используй независимый запуск выше.

## Демоаккаунты

| Роль | Почта | Пароль |
| --- | --- | --- |
| Клиент | client@fitlife.ru | Fitlife123! |
| Тренер | coach@fitlife.ru | Fitlife123! |
| Администратор | admin@fitlife.ru | Fitlife123! |

На странице входа кнопки ролей заполняют тестовые реквизиты. После этого нажми «Войти в кабинет». Регистрация создаёт только клиента. Роль нельзя выбрать в публичной форме.

## Что работает

- Гость: лендинг, направления, переходы к регистрации и входу.
- Авторизация: валидация, сообщение о неверных реквизитах, показ пароля, регистрация, выход, переход в кабинет своей роли.
- Клиент: поиск и фильтрация расписания, запись и отмена, контроль занятости и пересечений; дневник веса и жима лёжа с графиком, расчёт ИМТ при заданном росте; профиль; регистрация и отмена участия в событиях.
- Тренер: только своё расписание, создание и изменение занятий, отмена тренировки, просмотр участников и записей своих клиентов.
- Администратор: сводные показатели клуба, поиск клиентов, изменение профиля, абонемента и активности клиента, просмотр тренеров, управление общим расписанием, создание и редактирование событий, черновики и публикация, удаление событий.
- Общие элементы: формы в модальных окнах, подтверждение отмены/удаления, сообщения об ошибках, напоминания при открытом кабинете, мобильная навигация, адаптивные таблицы, поддержка клавиатуры и уменьшения анимации.

Все имена, показатели, события и записи в начальном наборе — вымышленные демонстрационные данные. Показатели обзора вычисляются из текущих данных, а не заданы как рекламные числа.

## Структура

```text
web/
  index.html                 # Гостевой лендинг
  landing.html               # Дополнительный адрес лендинга
  error.html                 # Страница ошибки
  auth/login.html            # Вход
  auth/register.html         # Регистрация
  panel/panel.html           # Кабинет клиента или тренера
  admin/panel.html           # Кабинет администратора
  assets/app.js              # Представления, формы и обработчики
  assets/store.js            # Деморепозиторий и правила операций
  assets/style.css           # Оформление и адаптивная верстка
  assets/favicon.svg
  server.mjs                 # Локальный статический сервер
  build.mjs                  # Сборка статических файлов в web/build
  start.cmd                  # Запуск на Windows
tests/store.test.mjs          # Автоматические проверки сценариев
```

Страницы соответствуют структуре из примера, но расположены в `web`, поскольку текущий проект использует отдельный frontend в nginx и не подключает Thymeleaf. HTML-файлы используют общие ES-модули. Не открывай их через `file://` — нужен HTTP-сервер.

## Деморежим и подключение backend

Сейчас в Spring Boot есть только основной класс приложения и заготовки `User`/`UsersRole`. Контроллеров, репозиториев, сущностей JPA и API авторизации нет. Поэтому frontend **не подключён к БД и серверной авторизации**.

`assets/store.js` хранит демонстрационные данные в `localStorage` под ключом `fitlife.demo.v1`, а идентификатор текущего пользователя — в `sessionStorage` под ключом `fitlife.session.v1`. Данные сохраняются после обновления страницы. Для нового браузера, другого порта или другого компьютера создаётся отдельный набор. Это не многопользовательская синхронизация. Для сброса удали эти два ключа в инструментах разработчика браузера и обнови страницу.

Для демонстрационных паролей используются PBKDF2, SHA-256 и случайная соль. Это не делает браузерное хранилище доверенным: пользователь может изменить свою локальную копию. Проверки ролей и защищённые маршруты здесь нужны для демонстрации UI. Используй только тестовые данные и пароли.

Для серверной интеграции замени методы `store.js` на обращения к реальному API и адаптируй загрузку данных в `app.js` под асинхронные запросы (сейчас чтение демоснимка синхронное). Сервер должен проверять роль, владельца записи, свободные места и конфликты внутри транзакции, а также хранить пароли и выдавать сессии. Не принимай роль, присланную браузером, как основание для доступа.

Предлагаемый контракт для последующей реализации; **это проект API, а не существующие endpoints**:

| Метод и маршрут | Назначение |
| --- | --- |
| POST /api/auth/login | Вход, сессия в HttpOnly cookie, ответ с профилем и ролью |
| POST /api/auth/register | Создание клиента |
| POST /api/auth/logout | Завершение сессии |
| GET /api/me, PATCH /api/me | Профиль пользователя |
| GET /api/schedule | Доступные роли занятия и тренеры |
| POST /api/bookings, DELETE /api/bookings/{id} | Запись и отмена |
| GET /api/progress, PUT /api/progress/{date} | Личный дневник |
| POST/PATCH/DELETE /api/trainings[/{id}] | Управление занятиями для тренера/администратора |
| GET /api/clients, PATCH /api/clients/{id} | Доступные роли клиенты и их данные |
| GET /api/events | События с учётом публикации |
| POST/PATCH/DELETE /api/events[/{id}] | Административное управление событиями |
| POST/DELETE /api/events/{id}/registration | Участие клиента |

Сохрани значения ролей проекта: `ROLE_USER`, `ROLE_COACH`, `ROLE_ADMIN`; `ROLE_SUPERADMIN` в интерфейсе имеет административные разделы. Для nginx понадобится same-origin proxy `/api` на Spring Boot, а для cookie-сессий — корректная CSRF-защита. Push, серверные уведомления, реальные платежи и покупка абонемента не реализованы.

## Проверки

Из корня проекта:

```powershell
node --test tests/store.test.mjs
node web/build.mjs
```

Восемь тестов проверяют вход, регистрацию и запрет выбора роли, заполнение мест и отмену, приватность и валидацию дневника, доступ тренера к своим занятиям, пересечения расписания, абонементы, публикацию событий и приостановку аккаунта. Тесты используют изолированную память, браузерные данные не затрагивают.

Проверены в браузере: лендинг, вход трёх ролей, запись и отмена, создание занятия тренером, изменение абонемента администратором и адаптивный вид. Сборка статических файлов прошла. Сборка Docker и запуск Java/backend не проверялись.
